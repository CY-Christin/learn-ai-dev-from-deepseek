# 跟着 DeepSeek 学习驾驭 AI 开发

> 拆解 deepseek-harness 仓库的开发方法论：一个两个月、12,000+ commits、几乎全由 AI 写出来的代码库，是靠什么没有散架的。

2026 年 8 月 13 日，DeepSeek 开源了 agent 框架 [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)（dsh）。发布后大部分解析都在讲"这个产品怎么用"，但这个仓库真正独特的价值在另一处：**它是目前公开可考的、规模最大的 AI 驱动开发实践样本**——完整的 git 历史、700+ 篇决策文档、11 个工作技能手册、4 篇事故复盘，把"一个团队如何用 AI 写代码"的全过程摊在了桌面上。

本仓库不讲 dsh 怎么用，只讲一件事：**他们是怎么用 AI 开发 dsh 的，其中哪些做法值得普通开发者和团队借鉴**。

所有材料来自对仓库 git 历史和文档的直接分析（截至 2026-08-15，master 分支，12,293 commits）。

## 一句话总结

**管两端，放中间。**

- **输入端**：给 agent 准确的事实——事实做成工具，不靠 prompt 里的叮嘱
- **输出端**：严格验收——能机械检查的全部写成 CI 门禁，不能机械检查的写进 review 手册，验收看外部世界不看 AI 自述
- **中间**：不规定 agent 怎么思考，没有任何一条规则试图约束模型的推理过程
- **所有规则从自己的事故和经验里蒸馏出来**，而不是预先规定；规则本身持续修订，甚至有半自动的修订流水线

## 这套方法论和"规范驱动开发"的区别

市面上流行的 AI 工作流方案（各类 spec-driven 框架、超长流程 prompt）大多是**预先规定（prescribe）**：先定一套通用流程，要求 AI 和人都遵守。dsh 走的是相反的方向——**蒸馏（distill）**：

| | 预先规定式 | dsh 的蒸馏式 |
|---|---|---|
| 规则来源 | 外部通用最佳实践 | 自己仓库的真实事故和经验 |
| 规则形态 | 流程模板、长 prompt | 短规则 + 链接 + CI 脚本兜底 |
| 约束对象 | AI 的行为过程 | AI 的输入（事实）和输出（验收） |
| 执行方式 | 依赖遵守 | 机器 gate 拒绝，或 review 手册指导 |
| 规则演化 | 版本发布 | 每次使用后同 PR 修订 |

这不是说"重流程"错了——dsh 的流程比大多数 spec 框架重得多。区别在于每一条重规则都满足两个条件：**从自己的坑里长出来**，以及**有 exit 非零的命令或明确的 review 步骤兜底**。满足不了的规则，他们自己也不定（他们明确否决过"用 CI 判断改动是否重要"——机械检查干不了语义判断）。

## 适用边界（诚实版）

这套体系建立在几个前提上，抄之前先对照：

1. **参与者全受控。** dsh 不接受外部 PR，写代码的是自己团队 + 自己配置的 agent。开放协作项目做不了这么狠的门禁。
2. **推理成本不敏感。** "我们是 DeepSeek——别省真实 API 测试"是他们的原话。100% 覆盖率、三件套双语文档、大规模快照回放，都以这个成本结构为前提。
3. **规模匹配。** 日均 200 commits、几十个 agent 分支并行时，防合并冲突、防文档漂移的机制才回本。单人小项目做全套是纯负担——他们自己的 review 维护工具就因为"单人使用、过全套门禁不划算"而被明着豁免出仓库，连豁免理由都留了案。
